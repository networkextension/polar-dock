# Polar 商业化定位 + 四赛道路线图

> 状态：2026-05-30 初稿。落盘供决策与对齐。
> 触发：#1 buildings 因现合作伙伴临近退休 + 下周碰施耐德（Schneider Electric），
> 成为时间敏感的第一楔子；#3 律所产品思考最成熟、技术最现成，作快速现金第二楔子。

---

## 0. 一句话定位

> **面向受监管/敏感行业的私有 AI 数据基础设施**
> ——采集、存储、推理、训练全链路客户自己拥有，数据不出域。

四个赛道不是四个产品，是同一条底座的四个垂直样板。它们形状一致：

```
边缘采集 → 安全多租户存储 → AI 推理 / 训练 → 协作 / 出报告
```

共同的护城河：数据敏感到不能上公有云——楼宇监控/能耗、人脸生物特征、
律师特权文件、患者 PHI。Polar 的「自托管 + 自有边缘 mesh + 私有多区域存储」
正是这件事的答案。

---

## 1. 平台底座 vs 垂直应用

横向骨架（已建）——四条赛道都吃：

| 能力 | 模块 / 现状 |
|---|---|
| 身份 + 协作 + 多机器人房间 | dock 核心（已上） |
| 边缘设备网 + WG mesh | polar-agent / polar-hosts（v4 agent 链已上） |
| 多区域私有对象存储 | assets 模块（多区域复制 / warm-pull / 签名 URL / 配额，已上） |
| LLM 调度 + 多模型分发 + 机器人 | LLM dispatch（B1-B4 计费已上） |
| 权限 + 审计 | RBAC（IsSiteAdmin / admin_audit_log，已上） |
| 计量钱包 | LLM billing wallet（预付 + 计量，部分已上） |

垂直应用 = 薄应用 + 领域模型 + 合规层，贴在上面。
**这意味着每个新赛道的新建量，主要在「领域模型 + 专用 AI 模型 + 合规」，
而不是重做基础设施。**

## 3. #1 楼宇 —— 施耐德会面准备（重点）

### 3.1 为什么是现在
- 现合作伙伴年纪高、准备退休 → **承接风险 + 升级机会**：与其找个同量级的人接班，
  不如借这次把施耐德这种全球级渠道引进来替代/升级原有渠道。
- 下周碰施耐德 → 需要一份「我们带来什么 / 怎么互补 / 合作怎么落」的清晰说法。

### 3.2 我们已经有的底子（贴代码）
`polar-buildings` 当前 commit 已落地：
- **物理层 10 表**：`sites → buildings → floors → zones → devices`。
- **工单**：`work_orders + work_order_events`，借 `polar-projects` 的
  `chat_thread_id + bot_user_id + llm_thread_id` 绑定 → **AI 运维助手**自动派单/总结。
- **巡检**：`inspections + inspection_items`，失败自动生成工单。
- **告警**：`alarms`，阈值/离线/手动/巡检失败触发，关联工单关闭即自动解除。
- **WS 事件通道** `/ws/buildings`（polar-sdk/wsbroker），告警/工单/巡检/设备状态实时推。
- 端口 `127.0.0.1:8100`。

**关键集成缝**：
- `buildings.host_id → polar_hosts.hosts(id)`：每栋楼对应一台**现场边缘 agent**。
- `devices.host_skill_id → 轮询 skill`：**每个设备由边缘 agent 上的一个 host skill 驱动**。
- → 施耐德的每个传感器/控制器/表计，就是一行 `device`，由一个 host skill 轮询；
  告警走 WS 通道，工单进 AI 派单。**这就是接入施耐德硬件的标准缝，不用为它改架构。**

### 3.3 施耐德互补叙事（一页话）
| | 施耐德带来 | Polar 带来 |
|---|---|---|
| 硬件/BMS | EcoStruxure、传感器、控制器、表计、楼宇自控 | —— |
| 边缘到云数据层 | —— | 自有边缘 agent mesh + 私有多区域存储，**数据不出域** |
| AI | —— | 多模型运维助手（派单/巡检/告警归因）、自然语言运维 |
| 多租户/合规 | —— | RBAC + 审计 + 邀请制租户 + 计量钱包 |
| 渠道/项目 | 全球集成商网络、品牌、项目源 | 软件产品 + 私有部署能力 |

一句话对外：**「施耐德的硬件 + Polar 的私有 AI 数据层」**——
客户的楼宇数据（能耗/门禁/监控/告警）留在自己机房，AI 在边缘和私有云上跑，
不进任何厂商的公有云。这正是施耐德 EcoStruxure 之外、客户最在意的那块。

### 3.4 合作模式（带去会面讨论的选项）
1. **OEM/白标**：Polar 软件嵌进施耐德方案，施耐德渠道卖，按部署/席位分成。
2. **技术集成伙伴**：保持双品牌，Polar 作 EcoStruxure 的「私有 AI 数据层」补充，
   联合 PoC → 联合参标。
3. **数据/AI 模块授权**：施耐德负责硬件+BMS，Polar 按楼宇数 + 存储/算力计量收费。

> 倾向：先 2（联合 PoC，低承诺、验证互补），跑出一个标杆楼再谈 1 的分成结构。

### 3.5 会面要的结果 / 要准备的材料
- **要的结果**：选 1 栋真实楼做联合 PoC，明确各自投入与时间表；明确数据归属=客户。
- **会前要补的材料**（落盘后我可以接着做）：
  - [ ] 一页架构图：施耐德设备 → 边缘 agent(host skill) → buildings-svc → WS/工单/AI。
  - [ ] `polar-buildings` REST 域处理器补齐（现在只有告警 CRUD + WS publisher 就位）。
  - [ ] 一个可演示的告警→AI 派单→工单闭环 demo（用 .57/dev 现成栈跑）。
  - [ ] 设备协议接入清单：BACnet/Modbus/MQTT —— 确认施耐德侧用哪几种。
  - [ ] 数据不出域的部署形态说明（边缘 agent + 私有 assets，离线/弱网可用）。

### 3.6 polar-buildings 近期 MVP 范围（PoC 用）
- 补 REST：sites/buildings/floors/zones/devices CRUD + 工单/巡检/告警全链路（WS 已就位）。
- 1 个设备协议适配（先挑施耐德主用的一种），落成一个 host skill。
- AI 运维助手：告警→归因→建议工单（复用 dock LLM dispatch + bot 绑定）。
- 看板：实时告警/工单/设备状态（吃 `/ws/buildings`）。
- 延后（schema 注释已标）：时序库、设备类型模板、巡检路线模板、照片 blob（接 assets）、逐条 ACL。

## 4. #3 律所不良资产 —— 快现金第二楔子

### 4.1 为什么排第二
技术最现成（几乎全是 dock 已有：LLM 多模型 + 文档 + RBAC + 审计 + 邀请制租户），
付费意愿最高，最快出 PoC 验证整条 LLM 栈。`polar-lawyer` 已有成熟产品/策略文档。

### 4.2 已有产品思考（polar-lawyer/doc/strategy-path.md）
不良资产案件的核心产品是**多 LLM 策略推演闭环**：诊断 → 证据 → 策略：
- **Claude** 生成法律路径 + 长链可行性论证；
- **GPT** 演对方律师，对每套策略给反制预测（带本土类案数字）；
- **DeepSeek** 提供大陆司法实践数据（审理周期、调解结案率、违约金支持比例）；
- **裁决器**不投票选最优，而是标「什么样的企业家适合走这条路」。
- 三套路径是「快/中/重」不是「好/中/差」；预期回收率给区间不给点估值；底部「混合策略」。
- 产品语言底线：**法律没有标准答案，只有匹配诉求的答案。**

> 这套「多模型分歧诚实展示 + 裁决器做诉求匹配」正是 Polar LLM dispatch 的杀手级展示。

### 4.3 缺口 / MVP
- `lawyer-schema.sql`：案件 / 当事人 / 证据 / 路径 / 文书 表（现是 placeholder）。
- 文档 RAG：合同/裁判文书入 assets → 切分 → 检索（私有，不出域）。
- 策略推演编排器：把上面四角色串成一次 dispatch（dock 多 LLM 已支持）。
- 文书工坊 + 「交叉审稿」 + 「导出见律师包」。
- 计费：按案 / 按回收比例（和 LLM 计量叠加）。

## 5. #2 观众表情捕捉 —— CV 能力建设 + 学院 reference

- **价值**：建起 Polar 第一条**视觉推理边缘管线**（采集→存→模型→出分析），
  规模小、学院预算有限，但是好 reference，且**给 #4 医学影像直接铺路**（同一形状）。
- **缺口**：人脸/表情 CV 推理插件（边缘 agent 上跑）、素材入 assets、看板。
- **风险（先于第一行采集代码定清）**：人脸=生物特征 PII。必须先定知情同意 + 脱敏/
  匿名化（只存聚合情绪曲线，不存可识别人脸）+ 数据用途与留存边界。

---

## 6. #4 医学影像训练 —— 旗舰（最后上）

- **价值**：TAM 最大，最贴 assets 多区域护城河（DICOM 大文件、多中心）。
- **缺口**：DICOM 接入、PHI 去标识、标注台、训练/GPU 编排。
- **为什么最后**：合规/监管/伦理/销售周期最长。等 #2 的视觉管线 + 脱敏层 +
  合规肌肉都练出来再上。
- **风险**：PHI + 伦理审查 + 数据可用性同意，法律暴露最高，事前定清。

---

## 7. 横向投资（一次建，四条都吃）

按 ROI 排：
1. **通用数据管线**：`ingest → assets → 标注 → 推理插件`，复用边缘 agent + host skill。
   （#1 设备轮询、#2 人脸采集、#4 DICOM 都是它的实例）
2. **PII/PHI/法务脱敏层**：人脸匿名化、PHI 去标识、法务红线脱敏 —— #2/#3/#4 都要。
3. **标注 + 训练工作区**：#2/#4 共用。
4. **计量/钱包**：存储 + 算力计量（LLM billing 已起步，扩到 assets 存储 + 推理）。

---

## 8. 计费模型

- 不用按座 SaaS（对这些客户都弱）。
- 默认：**预付钱包 + 存储/算力计量**（assets 配额 + LLM 计量基本现成；UI 用余额+充值，
  不用月度封顶编辑器）。
- #1：按楼宇数 / 按设备数 + 存储计量；或 OEM 分成。
- #3：按案 / 按回收比例 + LLM 计量。
- #2：项目制 + 数据集授权（注意同意边界）。
- #4：按数据量 + 训练算力计量 + 数据集授权。

## 10. 风险与红线

- **#2/#4 同意与脱敏**：人脸和 PHI 一旦采集即有法律暴露。**在写第一行采集代码前**
  定清知情同意、脱敏/匿名化、留存与用途边界，不能事后补。
- **#1 施耐德合作**：先低承诺（联合 PoC）验证互补，再谈分成/白标；数据归属=客户，写进 PoC 条款。
- **#3 律师特权**：文档全程私有、审计可查（admin_audit_log 已有），不出域。
- **承接风险（#1 伙伴退休）**：把领域知识/客户关系在退休前结构化沉淀到模块文档，别随人走。
