# Polar dock — HTTP API reference (for client & SDK authors)

This is the cross-cutting guide. The **authoritative, machine-readable** surface
is [`catalog.json`](./catalog.json) — 297 endpoints with method, path, auth tier,
and recovered request-body / query / path / header contracts. It is generated by
static analysis (`go run ./cmd/api-catalog-gen`) and also served live at
`GET /api/_catalog` (admin) alongside `GET /api/_routes` (the live gin route table).
Regenerate after adding/changing routes; CI should diff it.

> The iOS/Android SDKs are designed to **code-generate their request/response
> layer from `catalog.json`**. See [`../arch/mobile-sdk-design.md`](../arch/mobile-sdk-design.md).

| Env    | Base                              |

## Auth

Username/password → token family (access + refresh), rotating refresh tokens.

- `POST /api/register`, `POST /api/login` → **set httpOnly cookies**
  (`access_token`, `refresh_token` with `Path=/api/token`) and return
  `{ user_id, username, access_expires_in }`. **Tokens are NOT in the body** —
  they're cookie-only. (SDK implication below.)
- `POST /api/token/refresh` (send the refresh cookie) → rotates the family, sets
  new cookies, returns `{ access_expires_in }`. On replay/expiry → `401`, family
  revoked, client must re-login.
- `POST /api/logout` revokes the presented access token's family.
- Access TTL ≈ 30 min; refresh TTL ≈ 30 days.

**Two ways to authenticate a request** (`AuthMiddleware`):
1. **Cookie** `access_token=<jwt>` (browsers + any cookie-jar HTTP client).
2. **`Authorization: Bearer <jwt>`** — *wins over the cookie*, intended for
   third-party / native clients.

Device hint headers (optional, improve session records + push): `X-Device-Type`,
`X-Device-Id`, `X-Push-Token`.

> ⚠️ **SDK note:** because login returns tokens only as httpOnly cookies, a pure
> `Bearer` native client cannot read the JWT from the login response today. v1
> SDKs use the platform cookie jar (`HTTPCookieStorage` / OkHttp `CookieJar`);
> a body-token login variant for headless use is a tracked follow-up — see the
> SDK design doc.

## Active workspace (multi-tenant context)

Almost every resource is scoped to a **workspace** (a.k.a. team). The active
workspace is selected per-request by the **`X-Workspace-Id`** header. If omitted
or invalid (e.g. you were removed), `resolveActiveWorkspace` falls back to your
personal/home workspace — never an error. List your workspaces with
`GET /api/teams`. The SDK keeps the chosen id and injects the header on every call.

## Auth tiers (the `auth` field in catalog.json)

| tier          | meaning                                                          |
|---------------|------------------------------------------------------------------|
| `""` (open)   | no auth (login, register, public share routes)                   |
| `user`        | `AuthMiddleware` — any authenticated user                        |
| `admin`       | `AdminMiddleware` — **site admin** (root-team owner/admin)        |
| `plugin-hmac` | `/internal/v1/*` — module↔dock HMAC, not for app clients          |

Within `user`, finer-grained gates are enforced **inside** handlers via RBAC
`Can()` (see below) — the catalog's `auth` column won't show those; rely on
`GET /api/me/permissions` to know what the current user may do.

## RBAC — capability model (read this for UI gating)

Roles → permissions, resolved per workspace. The client uses it to **gate
affordances** (hide buttons the user can't use); the server enforces regardless.

- `GET /api/me` → `{ ..., site_admin: bool }`.
- `GET /api/me/permissions` → `{ workspace_id, permissions: string[], site_admin }`
  — the caller's effective permission keys in the active workspace.
- `GET /api/rbac/permissions` → the platform permission catalog.
- `GET/POST /api/teams/:id/member-roles` — list / assign member roles.
- `GET/POST /api/teams/:id/roles`, `PUT/DELETE /api/teams/:id/roles/:roleId` —
  per-workspace **custom roles** (system roles are global + read-only).

Permission keys today: `platform:admin`, `team:manage`, `llm:admin`,
`bot:admin`, `asset:write`, `prompt:admin`, `lawyer:*`. owner/admin/site-admin
short-circuit to full. Some enforcement is behind default-off flags
(`POLAR_ENFORCE_LLM_ADMIN`, `POLAR_ENFORCE_RESOURCE_RBAC`) — see
[`../arch/permission-model.md`](../arch/permission-model.md).

## Workspace resource mounts (南北向 sharing)

A workspace can **mount** another workspace's resources (read-only by default)
without copying. `GET/POST/DELETE /api/teams/:id/mounts`. Whether mounted
resources actually appear in list responses depends on the dock flag
`POLAR_WORKSPACE_MOUNTS`. Platform-level LLM configs (`is_platform`, set via
`POST /api/llm-configs/:id/platform`) are the always-on inheritance case.
See [`../arch/workspace-resource-visibility.md`](../arch/workspace-resource-visibility.md).

## Conventions

- **Content type:** JSON in/out. File uploads are `multipart/form-data`
  (assets, lawyer documents, expense receipts).
- **Errors:** `{ "error": "<message>" }` (often an i18n key or a Chinese string),
  with the HTTP status carrying the semantics: `400` bad input, `401`
  unauthenticated (→ refresh then retry, then re-login), `403` lacks
  permission/role, `404` not found, `409` conflict (uniqueness), `402` out of
  credit (LLM proxy), `5xx` server.
- **Pagination:** `?limit=` / `?offset=` or cursor where present (see per-route
  query fields in the catalog). Not yet uniform — the SDK normalizes per family.
- **Timestamps:** RFC3339 / ISO-8601 UTC.
- **IDs:** mostly opaque strings; some legacy numeric (`llm_configs.id`, asset id).

## Endpoint families (orientation; counts approximate)

| family | prefix | notes |
|--------|--------|-------|
| auth/session | `/api/login`,`/register`,`/token/refresh`,`/me`,`/logout` | |
| teams/workspaces | `/api/teams*` | membership, invites, roles, mounts |

| skills / agents / hosts | `/api/skills*`,`/api/agents*` (+ hosts subdomain) | device fleet |
| admin | `/api/admin/*` | site-admin only |
| meta | `/api/nav`, `/api/system/info`, `/api/_routes`, `/api/_catalog` | introspection |
